  • The window is finite and your repo isn't in it. The agent opens files on demand, and it opens the ones the task mentions.
  • When the window fills, older context gets summarised. Conventions it inferred are the first thing a summary drops.

Why the twentieth session is worse than the second

Nothing carries over.
Every session rebuilds its picture from a smaller slice.

  • Session ends, window's gone. The next one starts from zero, or from a summary that kept the task and lost the conventions.
  • The slice is chosen by what looks like the task, not by what set the convention. The file that established "we throw typed errors" isn't in it.
  • Once two ways coexist, the next session sees both and has no basis to choose. Every fork is a new place to fork.

The agent isn't getting dumber. The same policy is running on a shrinking view of a growing repo.

What we're chasing

Everything compiles.
Everything passes review.

Every fresh session starts with no memory of what your codebase already settled on. So it makes reasonable choices that aren't your choices.

  • One handler throws a typed error. The next might return a plain object.
  • Eight services go through the repository layer. The ninth on could reach for raw SQL.

Where we're at

VibeDrift is a governance layer
for coding agents.

It learns what your repo already does and holds the agent to it.

  • Fourteen detectors group files by directory, vote on what each group does, and flag what deviates. That part works and I'll show it in a second.
  • One rule: no finding without a peer group to deviate from. It keeps the tool honest.

What it's doing
while we wait

  • Groups files by directory, because conventions are local.
  • Votes on the dominant pattern in each group.
  • Needs 70% agreement before it calls anything a convention.
  • Weights code from this week about twice as heavily as code from three months ago.

Below the threshold it reports nothing. A repo that never agreed with itself has nothing to drift from.

The experiment

Same spec, built twice.

  • Track V has the tool in the agent's loop. Track C doesn't, and isn't supposed to know it exists.
  • Every sprint is a fresh session with no memory of the last one. That's the condition from slide 3, on purpose.
  • Acceptance tests written from the spec by agents that never saw either codebase. Protocol signed off before sprint zero.
  • Per sprint, both tracks: duplication, lint errors, circular deps, unguarded routes, and our own score. Re-derived from raw tool output, never from either track's self-report.

What went wrong running it

Run one is void. Here's how.

  • The control group wasn't blind. The architecture doc every session reads named both tracks and the tool. We found it by accident, with grep, weeks in.
  • One finding was retracted outright. It was a bug in our measurement script, not a difference between the tracks.
  • Then the tool itself turned out to be silently dropping files from the codebases we were measuring. That's issue #110. That voided the run.

We keep a numbered list of every known flaw in the harness itself. It's at 63. Run two is going as I stand here.

What's broke recently

Two of the twelve open bugs

  • #118. Drift Sessions silently stop checking once a repo passes 2,000 functions. No advisory, no error. Every edit passes, which reads as "not drifting" when it means "the checker turned itself off." Our own repo is one quarter of growth from tripping it.
  • #110. One long line and it drops the whole file, and records nothing when it does. This is the one that took our experiment with it.

Both fail silently, and silence reads as "you're fine." That's the one thing this tool can't afford to say by accident. The other ten are on the public tracker.
