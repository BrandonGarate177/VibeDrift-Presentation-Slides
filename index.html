What we're chasing

Everything compiles.
Everything passes review.

Every fresh session starts with no memory of what your codebase already settled on. So it makes reasonable choices that aren't your choices.

  • One handler throws a typed error. The next returns a plain object.
  • Eight services go through the repository layer. The ninth reaches for raw SQL.
  • Nobody notices until the third one.

What we built

It checks your codebase
against itself.

  • Groups files by directory and votes on what each group already does. The winner is the convention.
  • Flags what deviates from that, and points at the line.
  • Runs on your machine. No rulebook, no account, no network for the local scan.

That's the whole product. The rest of this is about whether it's any good.

The rule we gave ourselves

No finding
without a baseline.

It can't flag anything unless there's a peer group to deviate from. That keeps it honest. It also makes it hard to prove it works.

Where it runs

Before it writes,
not after you review.

An MCP server the agent can ask mid-session. Same baseline as the scan, so the in-loop answer can't disagree with the report.

claude mcp add vibedrift \
  -- npx -y @vibedrift/cli mcp

# agent, mid-edit:
validate_change(file, contents)
  → fits: true | false | null

Three answers. null means we're not sure, and we'd rather say that than guess.

Running now · ~20 seconds

What it's doing
while we wait

  • Groups files by directory, because conventions are local.
  • Votes on the dominant pattern in each group.
  • Needs 70% agreement before it calls anything a convention.
  • Weights code from this week about twice as heavily as code from three months ago.

Below the threshold it reports nothing. A repo that never agreed with itself has nothing to drift from.

What it gets wrong

Twelve open bugs, ours,
on the public tracker.

  • #110 — one long line makes it drop the whole file, and record nothing when it does.
  • #112 — signed-in scans upload raw source snippets. The telemetry opt-out doesn't cover it.
  • #118 — sessions silently stop checking past 2,000 functions.

github.com/VibeDrift/VibeDrift/issues · two of those three fail silently, which is the worst way to fail.

What we don't know

Does any of it work?

  • We can't rule out that the score is partly measuring repo size rather than drift.
  • So we built an experiment. Same spec built twice: one track with the tool in the agent's loop, one without. Fresh session every sprint. Protocol written and signed off before we ran anything.

Run one

The experiment found a bug in the tool, and the bug corrupted the measurement.

That's #110. It was silently dropping files from the codebases we were measuring. Run one is void.

The fix is on a branch. No PR yet. Run two is going as I stand here.

What that taught us

Three things we got wrong.

  • The thing measuring the experiment can corrupt the experiment. We should have audited the tool before trusting its output as a metric.
  • Blinding is harder than it looks. Our control group read a design doc that told it it was the control. Every sprint.
  • Our own repo drifted from our own AGENTS.md while we were building a tool to catch exactly that.

What we actually can't decide

Should it block
the agent, or just
tell you afterward?

We've gone back and forth. Blocking is annoying and might be the only thing that works. Telling you afterward is polite and might be useless. You'd know better than we do.
